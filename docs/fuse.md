# vulnwrench fuse

Trivy, Grype and OSV-Scanner rarely agree: the same vulnerability shows up under
different IDs, with different severities and fixed versions, or only in one tool.
`vulnwrench fuse` merges existing Trivy, Grype and OSV-Scanner JSON reports into one
deterministic package/version/advisory agreement and conflict matrix that keeps every
source observation and its provenance. Use it when you run more than one scanner and
need one deduplicated finding list without hiding where the scanners disagree.

_Formerly the standalone `vulnfuse` tool._

It does not run scanners, contact advisory services, evaluate target code or
establish that a package is safe. Standard library only; Python 3.11+.

## Quick start

```sh
pip install vulnwrench
vulnwrench fuse --help
vulnwrench fuse merge --trivy trivy.json --grype grype.json --osv osv.json --output merged.json --markdown merged.md
vulnwrench fuse explain --merged merged.json --finding f0001
vulnwrench fuse validate --merged merged.json
```

Subcommands:

| Subcommand | What it does |
| --- | --- |
| `merge` | Merge JSON reports, retaining every observation (`vulnfuse-1` JSON, optional Markdown summary) |
| `explain` | Trace one finding to its original alias, package, path and conflict evidence (JSON or Markdown) |
| `validate` | Check a complete saved merge without selecting a finding |
| `validate-input` | Check one scanner profile and summarize byte provenance and counts |
| `validate-coverage` | Check coverage-manifest/report bindings, or summarize coverage recorded in a saved merge |

To run the bundled synthetic example from a clone of the repository (recorded input
names are repository-relative, so run from the repository root):

```sh
vulnwrench fuse merge --trivy examples/fuse/trivy.json --grype examples/fuse/grype.json --osv examples/fuse/osv.json --output out.json --markdown out.md
python3 scripts/fuse/verify_examples.py
```

Verifier output:

```text
PASS three-format CLI: 6 observations -> 4 findings; transitive aliases; severity/fix conflicts
PASS committed JSON and Markdown match executed outputs; source SHA-256 and counts verified
PASS deterministic repeat: byte-identical JSON and Markdown
PASS recognized empty reports: 0 observations, 0 findings
PASS coverage manifest: target mismatch, incomplete scan and missing date; 2 findings retained; no fix inferred
PASS scan policy: same target/database, different suppression declarations; 1 finding retained; no fix inferred
PASS database snapshots: same target/policy/time, different identities; 1 finding retained; no fix inferred
PASS explanation: 2 alias links; 2 contributing observations; external alias evidence isolated; ambiguous selection exit 2
PASS saved explanation: identical evidence; dangling alias reference exit 2; output preserved
PASS unsupported schema, unreadable path and invalid JSON: exit 2; no content echoed
Verified all examples offline; no scanner or network access used.
```

The resulting [JSON](../examples/fuse/expected/merged.json) and
[Markdown](../examples/fuse/expected/merged.md) were generated by the CLI, not hand-written.
The example has two observations from each scanner. Three observations for
`pkg:npm/demo@1.0` join through the explicit chain
`CVE-2025-0001` ↔ `GHSA-demo-0001` ↔ `OSV-DEMO-0001`.
Its severities include HIGH and CRITICAL, and its fixed-version reports include
1.1 and 1.2: both conflicts remain visible. Three other findings stay separate
because of a different qualifier (`arch=arm64`), installed version (`2.0`) or
ecosystem (`pypi`). All IDs and details in the fixtures are synthetic.
The fixtures are described in [examples/fuse/README.md](../examples/fuse/README.md).

## Inputs, outputs and exit codes

Each scanner option may be repeated. At least one input is required; providing
all three is optional. Without `--output`, JSON goes to stdout. `--markdown FILE`
adds a human summary, while the JSON retains the full evidence. Inputs are file
paths; stdin, `-` as a stream, directories and compressed files are unsupported.

Output parents must already exist. Existing outputs are atomically replaced per
file, with private permissions (0600 on Linux); writing JSON and Markdown is not
a two-file transaction. Output paths cannot alias any input (including the optional coverage manifest) or each other,
including existing symbolic/hard links. All input validation completes before
output replacement. No gate, dry-run, package-manager hook or scanner is executed.

Exit codes: **0** successful merge/explanation/validation/help, **2** invalid arguments, invalid or
unsupported input, or I/O failure. There is no policy gate or exit-code-1 mode.
Errors omit user-supplied values and paths; they identify the scanner/source and
problem category without echoing report contents. Reports and outputs themselves
can contain sensitive data: only feed authorized inputs and protect outputs.

## Optional scanner input byte expectations

`merge`, scanner-mode `explain` and live `validate-coverage` accept repeatable
`--expect-input-sha256 SCANNER FILE EXPECTED`, independently of a coverage
manifest. `SCANNER` is exactly `trivy`, `grype` or `osv`; `FILE` must match a
supplied scanner input argument **string exactly**. For example, `trivy.json`
and `./trivy.json` are distinct keys, even when they refer to the same file.
`EXPECTED` is exactly 64 lowercase ASCII hex digits, without prefix, whitespace
or normalization. Obtain the expectation from a trusted source when byte
integrity matters; computing it from already altered bytes pins those bytes.

For example, from `examples/fuse/`:

```sh
vulnwrench fuse merge --trivy trivy.json --grype grype.json --osv osv.json --expect-input-sha256 trivy trivy.json 15b98d3ade943a1b89e6aa63a7d40256d0e8405829fdd53e73ae50b646063b0b
vulnwrench fuse explain --trivy trivy.json --grype grype.json --osv osv.json --expect-input-sha256 trivy trivy.json 15b98d3ade943a1b89e6aa63a7d40256d0e8405829fdd53e73ae50b646063b0b --advisory OSV-DEMO-0001 --package 'pkg:npm/demo@1.0'
```

The digest above binds the committed synthetic `trivy.json` bytes. Inputs may
be pinned partially or all at once. One declaration applies to every repeated
occurrence of the same scanner/input key; every occurrence remains separate
evidence. Duplicate declarations reject even if their digests agree. Unsupported
scanners, malformed/missing operands, unmatched/unused keys and mismatched
digests return sanitized exit **2**, empty stdout and no creation/replacement of
JSON or Markdown outputs. Saved `explain --merged`, `validate` and
`validate-coverage --merged` reject this option. Existing input/manifest and output alias protections apply.

The digest and parsed report come from the same bounded strict JSON read for
each input occurrence. Matching hashes still require complete scanner-profile
and any coverage-manifest validation. Omitted and matching expectations produce
identical merge/explanation bytes for identical inputs; schemas, ordering and
observations are unchanged. Formatting-only edits also change the digest.
Byte binding establishes no authenticity, advisory truth, scan completeness,
coverage equivalence, safety or remediation guarantee.

## Supported input contracts and field mappings

Compatibility is defined by the **following structural profiles**, not a claim
of support for every historical/current scanner release. Named, small fixtures
are listed in [examples/fuse/README.md](../examples/fuse/README.md). JSON must be strict UTF-8,
with no duplicate object keys, NaN, infinity or numbers overflowing a finite
Python float. Maximum input size is **32 MiB per file**. JSON formatting and
floating-point textual precision are not preserved; the exact original bytes
are SHA-256-digested, and decoded documents are retained as `rawReport`.

| Profile / observation collection | Package identity and version | Advisory links, severity, fixes and paths |
| --- | --- | --- |
| Trivy JSON: `Results[].Vulnerabilities[]` | `PkgIdentifier.PURL`, `PkgName`, `InstalledVersion`; result `Type` maps ecosystem | `VulnerabilityID`; **no** alias inference from title/URL/vendor metadata; `Severity`; comma-separated `FixedVersion`; result `Target` plus vulnerability `PkgPath` |
| Grype JSON: `matches[]` | `artifact.purl`, `artifact.name`, `artifact.version`, `artifact.type` | `vulnerability.id` links only to `relatedVulnerabilities[].id`; primary `vulnerability.severity` and `vulnerability.fix.{versions,state}`; `artifact.locations[].{path,accessPath,realPath}` |
| OSV-Scanner JSON: `results[].packages[].vulnerabilities[]` | wrapper `package.{purl,name,version,ecosystem}` | vulnerability `id`, `aliases[]`; textual `database_specific.severity` / `ecosystem_specific.severity`; raw `severity[].{type,score}`; matching `affected[].ranges[].events[].fixed`; result `source.path` |

Trivy `Results: []` or `Results: null` and omitted/null per-result
`Vulnerabilities` are recognized empty collections. Grype `matches: []` and OSV
`results: []` are recognized empties. Nonempty OSV results require `packages[]`,
and package wrappers require `package` and `vulnerabilities[]` (possibly empty).
A malformed observation fails the **entire** merge; it is not skipped. An empty
recognized array does not certify that a scan succeeded or covered an artifact.

Other root shapes (SARIF, SBOMs, the raw OSV API array, grouped-only OSV output,
HTML, YAML) and ambiguous roots containing multiple scanner root keys fail with
exit 2. Unknown extra fields **inside a recognized report** are retained in its
`rawReport` without being interpreted. For example, Grype `ignoredMatches`, Trivy
misconfigurations/secrets, OSV `groups`, suppressed findings and inventory records
are preserved as raw evidence but do not enter this vulnerability observation
count. Alias assertions from OSV `groups` are not used. Nothing in this tool
proves scan coverage, database freshness, target equivalence or execution success.

### Exact package identity, bounded normalization

A known package key is its canonical type, namespace/name, exact installed
version, all PURL qualifiers, and subpath. Qualifier order and percent encoding
are canonicalized; values are preserved. No semver, epoch, version-range,
repository or title equivalence is inferred. `1`, `1.0` and `v1.0` are different.
Absent qualifiers are unqualified identities; they are never filled from another
report. A qualified PURL therefore never merges with an unqualified identity.

| Canonical PURL type | Accepted case-insensitive ecosystem/type labels |
| --- | --- |
| `npm` | npm, node-pkg, javascript |
| `pypi` | PyPI, python, python-pkg |
| `maven` | Maven, java, java-archive, jar |
| `golang` | Go, golang, go-module, gomod, gobinary |
| `gem` | RubyGems, ruby, gem, gemspec |
| `cargo` | crates.io, rust, cargo |
| `nuget` | NuGet, dotnet |
| `deb` | deb, Debian |
| `rpm` | rpm |
| `apk` | apk, Alpine |

If no PURL is supplied, the seven language types above can use explicit
name/version/ecosystem evidence to construct an unqualified key. Scoped npm
names (`@scope/name`), Maven `group:artifact` names and Go module paths are split
conservatively. Maven requires a group when no PURL supplies it. PyPI names use
lowercase and `[-_.]+` → `-`; npm names/scopes and NuGet names use lowercase.
Other name casing is preserved. This is a finite normalization map, not a full
package manager validator or a general package-url implementation.

OS package types **require a PURL and a distribution namespace or `distro`
qualifier for a known identity**, since name/version alone loses distribution
context. A bare OS PURL is retained as unknown with `missing-os-distribution`. Unknown/missing ecosystems, distro-specific labels
such as `Debian:12` without a PURL, and well-formed unsupported PURL types remain
`known: false` with a reason. Each such observation is isolated into its own
finding, even if names and advisory IDs match. It is retained, never guessed or
dropped. An explicit supported PURL can establish identity even if its scanner
label is unknown; its qualifiers and namespace still matter.

PURLs use `pkg:type/[namespace/]name[@version][?key=value&...][#subpath]`.
The strict subset rejects empty/dot path segments, encoded slashes in a segment,
invalid escapes/UTF-8, empty qualifier values, duplicate qualifier keys, whitespace
or control characters in identity/version, inappropriate language namespaces and
malformed npm scopes. Missing installed versions, wrong JSON types, contradictory
reported/PURL versions or known ecosystems, and incompatible reported/PURL names
are errors. A PURL may supply a missing name/version; an installed version may
complete a versionless PURL. Bare reported artifact names are allowed when an
explicit PURL supplies their namespace; they must still match its package name.

### Evidence, conflicts and accounting

Only OSV `aliases` and Grype `relatedVulnerabilities` create alias edges. The
graph is global to the input set and transitive; claims are trusted as **input
assertions**, not independently verified. `findings[].ids` is the whole connected
component, including aliases never directly observed as a primary ID. Each
observation separately records its `originalId`, directly supplied `ids`, scanner,
paths, raw severity evidence and fixes. Original ID spelling/case is preserved.

Every supported collection element becomes exactly one observation. JSON includes
input SHA-256, byte count, scanner, `rawReport`, and observation count; each
observation has a source ID and JSON pointer into the raw document. The top-level,
per-input, per-scanner and per-finding counts conserve all supported observations.
Repeated input reports count repeatedly, rather than being silently deduplicated.
Output ordering is stable even if input argument order changes; changing filenames
or bytes changes provenance. JSON has no clock-dependent fields.

`scannerPresence` distinguishes `observed`, `not_observed` in supplied reports,
and `not_supplied`. `inputPresence` gives per-report presence when a scanner flag
is repeated. Missing findings are **not proof of safety**, and different source
paths/scanning policies can make absence comparisons inconclusive. Paths are
retained but do not split otherwise identical package/version/advisory groups.

Severity labels LOW, MEDIUM, HIGH, CRITICAL and NEGLIGIBLE are normalized;
MODERATE maps to MEDIUM. UNKNOWN, absent/vendor-specific labels and CVSS vectors
remain unknown evidence (retained verbatim); **no CVSS calculation** is attempted.
`severityConflict` means multiple different known labels were actually reported.
`severityAssessment` is `unknown`, `partial`, `consistent_observed` or `conflict`;
consistent observed evidence can come from just one scanner/observation. This is
not a consensus or a vote. OSV conflicting textual labels remain visible too.

Fix versions remain strings. `fixVersionConflict` compares distinct explicitly
reported version sets; `fixStateConflict` compares explicit states other than
`unknown`/`not-reported`; `fixConflict` is their union. Missing data does not count
as disagreement. Grype `not-fixed`/`wont-fix` is explicit evidence of an empty
version set. An empty Trivy FixedVersion means `not-reported`, not proof of no fix.
OSV fixed events are extracted only for an explicitly matching affected package
(with the same normalized identity/qualifiers). Their `basis` and affected indices
are retained. All fixed events for that package are collected; **no version-range
membership, branch applicability, withdrawal or reachability evaluation** occurs.
These are reported candidates for review, not a recommended upgrade or proof of
remediation. Nonmatching/unknown OSV affected data stays in `rawReport`.

## Explain one advisory/package finding

`explain` accepts the same repeated scanner flags and optional coverage manifest
as `merge`. It merges the reports, selects **exactly one** finding, and writes
deterministic `vulnfuse-explain-1` JSON to stdout or `--output FILE`:

```sh
vulnwrench fuse explain --trivy examples/fuse/explain/trivy.json --grype examples/fuse/explain/grype.json --osv examples/fuse/explain/osv.json --advisory OSV-EXPLAIN-1 --package 'pkg:npm/demo@1.0#apps/api'
```

This local synthetic fixture has **5 observations and 3 findings**. The selected
API finding has **2 observations**, IDs `CVE-EXPLAIN-1`, `GHSA-explain-1` and
`OSV-EXPLAIN-1`, HIGH/CRITICAL severity evidence and conflicting fix-version sets
`["1.1"]` / `["1.2"]`. It retains both conflicts without choosing a fix. The
same-name package at `pkg:npm/demo@1.0#apps/worker` stays separate, as does
`UNLINKED-EXPLAIN-1` on the API package. Neither contributes its 9.9/8.8 fix
observation to the selected finding. The complete executed output is committed
as [explanation.json](../examples/fuse/expected/explanation.json).

`finding` preserves the selected merge finding, including every contributing
observation and conflict/absence assessment. `aliasLinks` lists the actual
direct assertions throughout its global alias component, with `sourceId`,
`observationId`, `primaryIdPointer` and the exact alias-field `pointer`. It never
invents a direct edge for a transitive relationship. Repeated alias fields and
repeated report inputs retain their separate locations. In this fixture,
Grype asserts GHSA → CVE at `/matches/0/relatedVulnerabilities/0/id`; OSV asserts
OSV → GHSA at `/results/0/packages/0/vulnerabilities/0/aliases/0`.

`evidence` contains normalized observations, their original `rawObservation`,
and `packageEvidence` / `pathEvidence` entries with exact JSON pointers and
values from the scanner report. `inputs` retains source names, SHA-256 digests,
byte counts and coverage metadata; pointers address those original scanner
documents. Coverage manifest provenance is also retained when supplied.
Only selected observations and observations asserting links in this alias
component enter `evidence`. Links can originate from a different package:
the worker OSV observation here is explicitly marked
`contributesToFinding: false`. Its severity/fix evidence remains outside the
API finding's conflict calculations.

The selectors use exact, case-sensitive strings from the merge output:

- `--advisory ID --package IDENTITY` matches any explicitly linked ID in that
  finding's component and the exact canonical package identity. Names, URLs and
  similar-looking IDs create no aliases. The command performs no online lookup.
- `--advisory ID` works if that component occurs in only one finding.
- `--finding f0001` selects by the finding ID generated for the **same complete
  input set**, including unknown package identities. These positional IDs can
  change when inputs change. Do not combine this selector with advisory/package.

`groupingRules` states the existing merge rules: PURL **subpaths** are part of
package identity; scanner filesystem paths are provenance and do not split an
otherwise identical identity. Unknown package identities remain isolated per
observation, and unlinked advisory IDs remain separate even on the same package.
`remediationAssessment` is always `not-evaluated`: fixed versions are reported
candidates only, and absence never establishes remediation.

**Failure behavior:** removing `--package` from the example is ambiguous because
the component appears on API and worker packages. Missing/unknown or ambiguous
selectors, unsupported reports and I/O errors return **2**, with sanitized errors,
empty stdout and no output replacement on validation failure. The usual input
size/strict JSON limits and output alias protection apply. `--markdown FILE`
remains a merge-only option.

### Markdown explanation

Only `explain` accepts `--format json|markdown`; **JSON stays the default** and
explicit `--format json` produces the same bytes. Markdown uses the same live
or saved inputs, exact selectors, optional SHA-256 expectations and validation:

```sh
vulnwrench fuse explain --trivy examples/fuse/explain/trivy.json --grype examples/fuse/explain/grype.json --osv examples/fuse/explain/osv.json --advisory OSV-EXPLAIN-1 --package 'pkg:npm/demo@1.0#apps/api' --format markdown --output explanation.md
vulnwrench fuse explain --merged examples/fuse/explain/merged.json --finding f0001 --format markdown
```

`--output FILE` writes the selected format with the existing private atomic
replacement; omission writes it to stdout. Unsupported formats, mixed modes,
invalid data or byte expectations, ambiguous/no-match selectors and output
aliases return sanitized exit **2**, empty stdout and no output creation or
replacement. Validation and selection finish before rendering. `merge`,
`validate`, `validate-input` and `validate-coverage` reject `--format`; their
schemas and behavior are unchanged.

The deterministic Markdown shows the selected package and advisory component,
every conflict flag and reported severity/fix value, all absence assessments
and comparisons, direct alias assertions with both original ID pointers,
source/observation IDs, and source/manifest provenance. Contributing observations
and noncontributing alias witnesses have separate sections. The synthetic API
selection retains its **two contributors and one worker alias witness**, with
only the two reported direct links. Transitive membership adds no direct link,
and a witness's fix evidence does not enter the selected finding's conflicts.
`remediationAssessment` remains `not-evaluated`; reported fixes are candidates,
and absence cannot establish remediation.

Dynamic table values use character references for punctuation, line breaks,
backticks, angle brackets and other structural characters. Recorded paths and
pointers are inert evidence. A **Complete explanation JSON** appendix retains
the entire selected `vulnfuse-explain-1` object in a fence longer than every
backtick run in its serialized JSON, including arbitrary extension text.
This preserves the existing **unredacted disclosure scope**: complete raw
observations for contributors and alias witnesses, original package/path values,
metadata for every input and the complete raw coverage manifest when supplied,
including unrelated declarations. These can contain sensitive data. Markdown
escaping prevents structure injection; it does not redact or authenticate data.
Unrelated full scanner reports are not added to the selected explanation.

The exported `render_explanation_markdown(explanation) -> str` is a pure
presentation function for an **unmodified result of `explain_finding`** after
the existing live/saved validation. It returns a trailing-newline string without
mutating the object, opening recorded paths, selecting again, merging again or
evaluating remediation. It does not independently validate arbitrary explanation
objects. Identical live/saved explanation objects produce identical Markdown.

To explain a **saved merge**, use `--merged FILE` instead of scanner flags:

```sh
vulnwrench fuse explain --merged examples/fuse/explain/merged.json --advisory OSV-EXPLAIN-1 --package 'pkg:npm/demo@1.0#apps/api'
```

This produces the same bytes as [explanation.json](../examples/fuse/expected/explanation.json):
2 contributing observations, 2 direct alias links and 3 evidence observations.
Original scanner files and manifest files need not exist; their recorded paths
are retained as provenance and never opened. `--merged` excludes all scanner
flags and `--coverage-manifest`. The same advisory/package or finding selectors,
stdout/`--output`, exit codes and saved-input symlink/hardlink protection apply.

Optionally bind the saved container to an expected **exact file-byte SHA-256**:

```sh
vulnwrench fuse explain --merged examples/fuse/explain/merged.json --merged-sha256 17a6b058d559da3dcc2d5a0e13b0947aa1ca0eed3fdb8262e7d302ccfcafb220 --advisory OSV-EXPLAIN-1 --package 'pkg:npm/demo@1.0#apps/api'
```

This digest is for the committed synthetic saved fixture. For your files, supply
an expectation obtained from a trusted record of the intended bytes. Computing
a digest from an already altered file only pins those altered bytes.
`--merged-sha256 EXPECTED` requires `--merged` and exactly 64 lowercase ASCII
hex digits, with no prefix or whitespace. Omitting it keeps the existing
consistency-only behavior; supplying no value is an argument error. A malformed
or mismatched expectation returns sanitized exit **2**, no JSON stdout and no
output creation/replacement. Neither digests nor paths are echoed in errors.
Formatting changes (including whitespace, line endings and object key order)
change the byte digest, even if the decoded evidence is identical. The digest
and decoded document come from the same bounded read. After strict JSON decoding,
the digest is checked before reconstruction and selection; a match still requires
all validation below and produces the same deterministic explanation bytes.
The option binds bytes to a caller expectation; it does **not** verify authorship,
advisory truth, scan execution or remediation. It adds no output fields and
does not verify the embedded original scanner/manifest file-byte assertions.

Before selection, `vulnwrench fuse` reconstructs the **entire** merge from embedded
`inputs[].rawReport` and `coverageManifest.rawManifest`, then requires exact
agreement with the saved report. This validates source IDs, observation IDs and
pointers, alias endpoints/bases/observation references, grouping, counts, conflicts
and coverage assessments, including evidence outside the selected finding.
It rejects missing/extra derived fields and changes to canonical derived-array
ordering rather than repairing them. Scanner extension data remains raw evidence.
JSON object key order and whitespace may differ. Input must use the complete
current `vulnfuse-1` output profile (including coverage, scan-policy and
database-identity fields); older or extended profiles are not migrated. Saved
files from before `databaseIdentity` was added must be regenerated from original
inputs; missing derived fields are rejected rather than silently repaired. The strict JSON and **32 MiB limit
apply to the whole saved file**, which may be larger than individual scanner files.

`sha256`, positive integer `byteCount` and `digestKind` are validated structurally.
For `canonical-json-bytes`, the digest and size are recomputed. For `file-bytes`,
they remain recorded assertions: decoded `rawReport`/`rawManifest` cannot recover
original formatting. Validation proves internal consistency, **not authenticity**;
a self-consistent rewrite can pass. Alias and coverage declarations remain
unverified input assertions, and absence never establishes fixed.

[The dangling-alias fixture](../examples/fuse/explain/dangling-alias.json) differs from
the valid saved fixture only in one alias edge's `observationId`. It fails with
sanitized exit **2**, no JSON stdout and no replacement of existing output,
even when the selector would otherwise match nothing. Unsupported schemas,
malformed metadata, inconsistent references or summaries behave the same way.

## Validate a complete saved merge

Validate a saved report without selecting a finding, including reports with zero
findings:

```sh
vulnwrench fuse validate --merged examples/fuse/explain/merged.json --merged-sha256 17a6b058d559da3dcc2d5a0e13b0947aa1ca0eed3fdb8262e7d302ccfcafb220
```

Success returns exit **0** and a deterministic `vulnfuse-validation-1` JSON summary:

```json
{
  "schemaVersion": "vulnfuse-validation-1",
  "validatedSchemaVersion": "vulnfuse-1",
  "validation": "internally-consistent",
  "container": {
    "sha256": "17a6b058d559da3dcc2d5a0e13b0947aa1ca0eed3fdb8262e7d302ccfcafb220",
    "byteCount": 19016,
    "digestKind": "file-bytes"
  },
  "inputCount": 3,
  "findingCount": 3,
  "observationCount": 5
}
```

The summary's digest and byte count describe the exact saved file bytes from the
same read used for validation. Formatting changes alter this metadata. Counts
come from the fully reconstructed evidence graph. No source paths or raw evidence
are included. `--output FILE` writes the summary atomically with private permissions
and leaves stdout empty; otherwise the summary goes to stdout.

`--merged` is required. The optional `--merged-sha256 EXPECTED` has the same format
and byte-binding contract as `explain`. Scanner, coverage-manifest, finding,
advisory, package and Markdown options are unsupported. Strict JSON, the 32 MiB
whole-file limit, complete current-profile reconstruction and input-alias output
protection all apply. Invalid arguments, malformed/mismatched expectations or
inconsistent evidence return sanitized exit **2**, empty stdout and no output
creation/replacement. A matching digest still requires full graph validation.

`internally-consistent` establishes internal consistency only. It does not verify
authorship, advisory truth, scan execution or remediation, and embedded original
file-byte provenance remains asserted. The equivalent library call is
`validate_merged(path, expected_sha256=None)`, exported from `vulnwrench.fuse`; it returns
the summary dictionary or raises sanitized `InputError` without writing output.

## Validate one scanner input

Check one supported scanner profile without emitting its raw evidence archive:

```sh
vulnwrench fuse validate-input --scanner trivy --input examples/fuse/trivy.json --input-sha256 15b98d3ade943a1b89e6aa63a7d40256d0e8405829fdd53e73ae50b646063b0b
```

Success returns exit **0** and this deterministic `vulnfuse-input-validation-1`
summary (JSON keys are sorted in the actual output):

```json
{
  "schemaVersion": "vulnfuse-input-validation-1",
  "validation": "profile-valid",
  "scanner": "trivy",
  "input": {
    "sha256": "15b98d3ade943a1b89e6aa63a7d40256d0e8405829fdd53e73ae50b646063b0b",
    "byteCount": 972,
    "digestKind": "file-bytes"
  },
  "observationCount": 2,
  "findingCount": 2
}
```

Both `--scanner` (exactly `trivy`, `grype` or `osv`) and `--input FILE` are
required. Optional `--input-sha256 EXPECTED` accepts exactly **64 lowercase ASCII
hex digits**. Omission checks the profile without a caller byte expectation.
The digest, byte count and decoded report come from the same bounded strict JSON
read; formatting changes require a new expectation. A matching digest still
requires complete adapter validation, including nested fields in recognized empty
collections and observations after otherwise valid data.

Counts use the existing **single-report merge** rules: every supported observation
is counted, explicit advisory aliases join only within the same known package
identity, and unknown identities remain isolated. Recognized empty reports have
zero observations/findings. Unknown fields and ignored/suppressed/non-vulnerability
collections do not add observations. Summary output contains no input path, raw
report, advisory/package details or evidence archive. Validation still processes
the full report in memory; it does not provide streaming or a reduced memory bound.

`--output FILE` uses the same private atomic writer and leaves stdout empty;

## Optional coverage manifest

`merge --coverage-manifest FILE` accepts caller declarations about each report's
target, scanner completion, database timestamp, scan policy and database snapshot
identities. It does **not** infer these from scanner metadata or verify them. The
existing merge remains available
without a manifest: every input has unknown coverage with
`reasonCodes: ["manifest-not-supplied"]`. Finding identities, observations,
conflicts and presence fields retain their existing meaning. Coverage fields
are additive to the `vulnfuse-1` output contract.

Optionally pin the manifest's exact bytes with
`--coverage-manifest-sha256 EXPECTED` in `merge` or scanner-mode `explain`.
`EXPECTED` must be exactly 64 lowercase ASCII hex digits, with no prefix or
whitespace. The flag requires `--coverage-manifest` and is rejected in saved
`explain` and `validate` modes. Omission preserves the existing behavior.
Malformed syntax is rejected before reading the manifest; the digest is compared
after the single bounded strict JSON read and before using its declarations.
A matching hash still requires full schema, declaration and report-binding
validation. Malformed/missing/mismatched expectations, forbidden modes and invalid
manifests return sanitized exit **2**, empty stdout and no JSON or Markdown output
creation/replacement. Existing input/manifest alias protections still apply.

Matching and omitted expectations produce identical output bytes for identical
inputs; no output schema changes. Formatting changes and self-consistent
declaration rewrites need their own expected digests. The check binds exact bytes
to a caller expectation, without establishing authorship, coverage truth,
database equivalence, safety or remediation.

The manifest is strict JSON, with exactly `schemaVersion` and `inputs` at its root:

```json
{
  "schemaVersion": "vulnfuse-coverage-1",
  "inputs": [
    {
      "scanner": "trivy",
      "input": "trivy.json",
      "sha256": "15b98d3ade943a1b89e6aa63a7d40256d0e8405829fdd53e73ae50b646063b0b",
      "targetIdentity": "release:demo-build-1",
      "scanComplete": true,
      "databaseTimestamp": "2026-11-10T12:00:00Z",
      "scanPolicyIdentity": "synthetic:suppress:none",
      "databaseIdentity": "synthetic:snapshot:A"
    }
  ]
}
```

Use the actual SHA-256 of the report's bytes (the runnable fixture is
[examples/fuse/coverage.json](../examples/fuse/coverage.json)). `scanner`, `input` and
lowercase 64-digit `sha256` are required and must match a supplied report.
`input` is the **exact report argument string**, with no path resolution relative
to the manifest. One entry covers repeated occurrences of the same report key.
Duplicate entries, unmatched/stale bindings, unknown fields and malformed values
reject the entire merge with exit 2 before replacing output. Missing entries
are allowed and yield `manifest-entry-missing`.

`targetIdentity` is an opaque, case-sensitive identifier; prefer an immutable
artifact digest rather than a mutable tag. `scanComplete` is boolean.
`databaseTimestamp` uses `YYYY-MM-DDTHH:MM:SS[.ffffff]Z` or a numeric `±HH:MM`
offset; timezone, seconds and a valid calendar date are required. Up to six
fractional digits are supported; leap seconds and unknown offset `-00:00` are
unsupported. Any of these five coverage fields may be omitted or null, explicitly
leaving that part of coverage unknown. The same 32 MiB/strict JSON rules apply
to the manifest as to reports.

`scanPolicyIdentity` is an opaque, case-sensitive string identifying the effective
scan policy, including suppression/ignore rules and filtering options. Prefer a
digest of the complete effective configuration. `vulnwrench fuse` does not compute that
digest, evaluate the policy or verify its label. Like `targetIdentity`, a supplied
string must be nonempty with no surrounding whitespace, control characters or
invalid Unicode; internal spaces and valid Unicode are preserved. Labels are
compared exactly, without normalization or interpretation. Omission and null both
yield `scan-policy-identity-missing`; older manifests remain accepted but their
coverage assessments now stay `unknown` unless a known mismatch takes precedence.

`databaseIdentity` is an opaque, case-sensitive string identifying the database
snapshot. Prefer an immutable snapshot/content digest; `vulnwrench fuse` does not compute
or verify it, infer it from scanner metadata, or equate snapshots across scanners.
It follows the same string rules as `scanPolicyIdentity`: no empty string,
surrounding whitespace, ASCII control characters/DEL or Unicode surrogates;
internal spaces and valid Unicode are preserved. Comparison is exact, without
case folding or Unicode normalization. Distinct non-null labels yield
`database-identity-mismatch`, even when timestamps represent the same instant.
Omission and null both yield `database-identity-missing`. Older manifests remain
accepted with unknown database identity; a known mismatch or incomplete scan
still takes precedence. Equal labels are unverified assertions and do not
establish equivalent contents, freshness or remediation. Timestamp and identity
comparisons are independent: an equal label does not override a timestamp mismatch.

Each input's `coverage` retains the declarations, local reason codes, and a
`manifestPointer` into `coverageManifest.rawManifest`. That top-level object
also records the manifest's exact byte SHA-256, byte count and input name.
Observation `sourceId` → input byte digest → manifest entry provides the full
provenance chain. No manifest means `coverageManifest: null`.
`coverage.scanPolicyIdentity` and `coverage.databaseIdentity` are always present,
using null when undeclared. Null and omission remain distinguishable in
`rawManifest`; without a manifest or matching entry the existing
`manifest-not-supplied` / `manifest-entry-missing` reasons apply.

For each finding, `absenceAssessments` compares every absent input with **all**
inputs observing that finding. It retains each comparison under `comparedTo`:

| Reason code | Meaning |
| --- | --- |
| `manifest-not-supplied`, `manifest-entry-missing` | No coverage declaration available |
| `target-identity-missing`, `scan-completion-unknown`, `database-timestamp-missing`, `scan-policy-identity-missing`, `database-identity-missing` | Comparison metadata unknown |
| `target-mismatch` | Declared target identifiers differ |
| `scan-incomplete` | At least one compared scan explicitly did not complete |
| `database-timestamp-mismatch` | Declared database timestamps represent different instants |
| `scan-policy-mismatch` | Non-null declared scan policy identities differ |
| `database-identity-mismatch` | Non-null declared database snapshot identities differ |

A comparison is `incomparable` if any known mismatch or incomplete scan exists,
otherwise `unknown` if any required metadata is missing, otherwise `comparable`.
The aggregate uses the same precedence and includes every reason. Timestamp
offsets are normalized for comparison. Equal timestamps only mean equal declared
instants, **not** equivalent scanner databases or verified freshness. Comparable
metadata, including equal policy and snapshot labels, does not verify equivalent scan policies,
inventory or suppression rules. **Every absence assessment has
`canEstablishFixed: false`**, including comparable ones; no coverage declaration turns an absent finding into a remediation claim.
JSON and Markdown both surface these assessments; no findings are discarded.
The top-level `coverageAssessment` also compares all supplied declarations,
including empty reports and reports that all observe the same findings. It uses
the same reason codes and precedence, so coverage differences remain visible
even when there are no absences to assess. For a single input it assesses that
declaration's completeness only; it never establishes a comparison with an
unsupplied report.

## Library

After installing vulnwrench:

```python
from vulnwrench.fuse import Report, dumps, merge_reports, read_report, render_markdown

merged = merge_reports([
    read_report("trivy", "examples/fuse/trivy.json"),
    read_report("grype", "examples/fuse/grype.json"),
    read_report("osv", "examples/fuse/osv.json"),
])
assert merged["observationCount"] == 6
json_text = dumps(merged)
markdown_text = render_markdown(merged)

# In-memory integrations use SHA-256 over canonical JSON bytes instead of a file.
empty = merge_reports([Report.from_document("osv", {"results": []})])
assert empty["findingCount"] == 0

```

Explain an unmodified library merge result without changing it:

```python
from vulnwrench.fuse import explain_finding

explanation = explain_finding(merged, advisory="OSV-DEMO-0001", package="pkg:npm/demo@1.0")
assert explanation["finding"]["observationCount"] == 3
assert explanation["remediationAssessment"] == "not-evaluated"
```

`explain_finding(merged, finding_id="f0001")` is the alternative selector. The
result is detached from `merged`; missing/ambiguous/invalid selectors raise
`InputError`. Pass an unmodified `merge_reports` result, not arbitrary JSON.
For a saved file, use `read_merged` to validate it first:

```python
from vulnwrench.fuse import read_merged

saved = read_merged("examples/fuse/explain/merged.json")
explanation = explain_finding(saved, advisory="OSV-EXPLAIN-1", package="pkg:npm/demo@1.0#apps/api")
assert explanation["finding"]["observationCount"] == 2
```

`read_merged` raises sanitized `InputError` on inconsistent or unsupported saved
reports and performs no I/O against paths recorded inside them.
`read_merged(path, expected_sha256=expected)` provides the same optional exact
container-byte check. The keyword-only value is `None` (default, no expectation)
or a string of exactly 64 lowercase hex digits; other types, malformed strings
and mismatches raise sanitized `InputError`. Full graph validation still applies.

With `examples/fuse/` as the working directory:

```python
from vulnwrench.fuse import merge_reports, read_report, read_coverage_manifest

covered = merge_reports(
    [read_report("trivy", "trivy.json"), read_report("grype", "grype-empty.json"),
     read_report("osv", "osv-empty.json")],
    coverage_manifest=read_coverage_manifest("coverage.json"))
assert (covered["observationCount"], covered["findingCount"]) == (2, 2)
```

`read_report` / `merge_reports` raise `vulnwrench.fuse.InputError` for unsupported inputs.
`read_report(scanner, path, *, expected_sha256=None)` optionally binds the exact
file bytes from its single read. `None` (default) omits the check; otherwise the
value must be a string of exactly 64 lowercase ASCII hex digits. Invalid types,
malformed values and mismatches raise sanitized `InputError`; scanner and digest
syntax checks occur before I/O. Scanner-profile and coverage validation still
occurs in `merge_reports`, including for matching digests. No output I/O or
authenticity/remediation claim is added.
Each source has `digestKind`: `file-bytes` for `read_report`, or
`canonical-json-bytes` for `Report.from_document`. Pass JSON-compatible objects;
do not mutate reports or manifests after reading/constructing them.
`CoverageManifest.from_document(document, input_name="memory")` supports in-memory
declarations, with canonical JSON byte provenance; entries bind to each
`Report`'s input name and digest. Manifest schema/bindings are validated by
`merge_reports`. The library itself performs no output I/O.
`read_coverage_manifest(path, expected_sha256=expected)` optionally checks the
same read's exact file bytes. The keyword-only expectation is `None` (default)
or exactly 64 lowercase hex digits; invalid types, malformed strings and
mismatches raise sanitized `InputError`. Manifest semantic and report-binding
validation still occurs in `merge_reports`, even after a matching digest.
Markdown escapes untrusted report text and is a summary, not a lossless archive.

## Upstream relationship and scope

This independent MIT implementation integrates documented report fields; it
copies no scanner implementation or rules. [THIRD_PARTY.md](../THIRD_PARTY.md)
identifies Trivy, Grype and OSV-Scanner and their Apache-2.0 license sources.

Grype already addresses some alias duplication ([#3511](https://github.com/anchore/grype/issues/3511)
is closed). [#1202](https://github.com/anchore/grype/issues/1202)
is background evidence about duplicate IDs and fix differences, not proof that
all current versions have that defect. Trivy/Grype outputs and multi-scanner
platforms already aggregate findings. The narrower purpose of `vulnwrench fuse` is a
small, offline cross-scanner evidence/conflict matrix with original observations and
explicit accounting; it is neither a new vulnerability detector nor a claim of
unique aggregation. No online lookup, scanner invocation, exploit checks,
policy gate, missing-vulnerability detection or VEX is included; see
[`vulnwrench exploit`](exploit.md), [`vulnwrench sarif`](sarif.md) and
[`vulnwrench triage`](triage.md) for those jobs.
